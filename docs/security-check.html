🔒 いまの設計のまま作ると危ないところ

ログインと管理者ビューが入ったので、アプリ側の粗をぜんぶ洗った。設計のバグが3つ出た。

🎯 いま直すべきは4つ。どれも「実装で気をつける」ではなく設計そのものが間違っているもの。
そのうち 1つは私が前に出した RLS ポリシーのバグ。先に謝っておきます。

🚨 いま直す4つ

BUG 1🪪 一般社員が 自分を管理者に昇格できる
私が前に出したのはこのポリシー。
create policy "自分の行だけ直せる" on users for update using (id = auth.uid());

Postgres の update ポリシーは「どの行を」しか縛れない。「どの列を」は縛れない。
つまり自分の行なら role も書き換えられる。ブラウザから1行投げるだけで管理者になれる。
update users set role='admin' where id = 自分;
✅ 直し方はいちばん簡単な形でいい。users に update ポリシーを作らない。
ポリシーがなければブラウザからは1文字も書けない。表示名の変更などはサーバー側（API Route）を通す。画面が少ないので負担はほぼゼロ。

列単位で守るトリガーを書く手もあるが、「書けない」を保証するほうが読んで分かる 
-- users は読むだけ。update ポリシーは作らない
create policy "社員は全員読める" on users
  for select to authenticated using (true);
-- ★ for update のポリシーは 意図的に作らない
BUG 2📣 LLM が出した宛先を そのまま使ってしまう
B は「誰に打診するか」を LLM に決めさせる。返ってきた user_id をそのまま ask.invite に渡すと、インジェクションで任意の人に通知を送れる。

前に「打診スパム」を危険として挙げたが、入口を塞ぐだけでは足りなかった。ツールの引数そのものを疑う必要がある。
✅ 候補リストを先にコードで作って、LLM の答えがその中にあるか確かめる。
LLM に自由な ID を書かせない。選ばせるだけにする。外れていたら実行せず 🚨例外の門へ。 
-- ① 候補はコードが DB から引く（LLMは関与しない）
const candidates = await db.query(...)   // [uuid, uuid, uuid]

-- ② LLM には「この中から選べ」と渡す
-- ③ 返ってきた答えを必ず照合する
if (!candidates.includes(llm.pick)) throw new Error('候補外')
📸
これ①の証拠になる。「候補外のIDを返させて 実行されずに止まる画面」は撮りやすい
BUG 3🚪 エージェントのエンドポイントが誰でも叩ける
B は1日1回 自分で起きる。その実体は /api/agent/organizer のような URL になる。
URL を知っていれば誰でも叩ける。連打されるとクレジットが溶けるし、打診が大量に飛ぶ。

OrcaRouter の予算上限は被害の天井であって 入口の鍵ではない。
✅ Cron からの呼び出しだけを通す。秘密の文字列を1本持って、合わなければ即 401。3行で済む。 
// Vercel Cron は Authorization ヘッダを付けて呼ぶ
export async function GET(req) {
  if (req.headers.get('authorization') !== `Bearer ${process.env.CRON_SECRET}`)
    return new Response('unauthorized', { status: 401 })
  ...
}
BUG 4🔑 service_role キーがブラウザに焼き込まれる
個人開発でいちばんよく起きる事故。NEXT_PUBLIC_ を付けなくても、"use client" のファイルから import すると混ざる。1度ビルドが通ってしまうと気づけない。
✅ service_role を読むファイルの1行目に import 'server-only' を書く。
クライアントから import された瞬間にビルドが落ちる。人間の注意力ではなくビルドに守らせる。 
import 'server-only'   // ← これだけ

export const admin = createClient(
  process.env.NEXT_PUBLIC_SUPABASE_URL,
  process.env.SUPABASE_SERVICE_ROLE_KEY
)

📝 やらないと決めて 正直に書く3つ

書くほうが点が上がる

  • マルチテナント分離：今回は1社前提。複数社に出すなら全テーブルに org_id を足して RLS の条件に入れる、と設計だけ書く
  • キーの分離：A と B のキーは分けたが同じプロセスにある。防いでいるのは事故であって攻撃ではない。本番なら B を別の実行環境に置く
  • カレンダー連携：デモはダミー。本番は Outlook の FreeBusy を叩く。予定のタイトルは最初から取りに行かない設計
✍️
「ここまでやった／ここからはやっていない」の線が引けているチームは強い。穴がないふりをするより、穴の位置を正確に言えるほうが①でも③でも評価される

💾 まとめて流すSQL

-- BUG1 users は読むだけにする（update ポリシーを作らない）
alter table users enable row level security;
create policy "社員は全員読める" on users
  for select to authenticated using (true);

-- #10 なりすまし防止：user_id はDBが埋める
alter table messages alter column user_id set default auth.uid();

alter table messages enable row level security;
create policy "ライブの参加者は読める" on messages
  for select to authenticated using (true);
create policy "自分としてだけ投稿できる" on messages
  for insert to authenticated
  with check (user_id = auth.uid() and is_agent = false);

-- #04 新しいテーブルにも RLS を
alter table lives             enable row level security;
alter table live_participants enable row level security;
alter table calendar_events   enable row level security;

create policy "ライブは全員見える" on lives
  for select to authenticated using (true);
create policy "参加者は全員見える" on live_participants
  for select to authenticated using (true);

-- 予定は本人だけ。エージェントは service_role で素通りする
create policy "自分の予定だけ見える" on calendar_events
  for select to authenticated using (user_id = auth.uid());
🗓️
calendar_events を本人だけにしておくのが大事。他人の空き時間が見えるのは それ自体が情報漏洩。日程調整は service_role で動くエージェントだけがやる
