💬 部屋でチャットもできるようにする

A のトリガーとテーブルがどう変わるか。結論から言うと 得のほうが大きい。

🎯 変更は小さい。テーブルは1枚のリネームと1枚の昇格だけ。
そしてトリガーは「会が終わったら」から「会話のかたまりが閉じたら」に一般化される。音声もチャットも同じ概念で扱えるようになる。
📌
そもそも画面はもうチャット前提だった。小室さんが作っているのは「グループチャットの入室画面」と「トーク画面」のモック。設計が画面に追いついていなかっただけで、こちらを直すのが正しい

⏰ トリガーをどう一般化するか

音声には「終わり」があるがチャットにはない。ここが唯一の難所。

🎤 音声
通話が切れる＝はっきりした区切り
切れ目：通話終了
➜
💬 チャット
終わりがない。ずっと続く
切れ目：30分の沈黙
🧩 どちらも「会話のかたまりが閉じた」
A のトリガーはこれ1つ。音声かチャットかは中身の違いであって 起動条件の違いではない

🤖 切れ目の判定はAIにさせない

やり方どうなるか判定
メッセージが来るたびに走る1行ごとにLLM。高いうえに文脈が足りない（1行では知見にならない）❌
AIに「ここで切っていいか」を判断させるA が Lv.3 になってしまい自律の心臓が2つになる。Bとの役割分担が崩れる❌
ルールで切る（30分沈黙 または 100件）安い・読める・壊れにくい。A は Lv.2 自動化のままでいられる✅
🫀
自律の心臓は B ひとつに集中させる。A まで賢くすると「どこが自律なのか」が説明しづらくなる。あえてルールで切るのは設計判断であって手抜きではない

🗃️ テーブルの変更

いまこれから理由
meetingssessions「会議」ではなく会話のかたまりになった。kind で voice / chat を分ける
transcript_idsource_refチャットには元のトランスクリプトがない。NULL を許す
messages ⚪ 画面のためmessages 🔴 コアA の入力になったので昇格
—messages.session_idNULL なら未処理。これだけで冪等性が出る
🔑
二重取り込みの守りが自然に効く。音声は source_ref が UNIQUE、チャットは session_id が埋まったら処理済み。A が拾うのは session_id is null の発言だけなので、同じ発言を2回拾えない

🚨 新しい落とし穴がひとつ

AIの発言を A の入力にしてはいけない

B は部屋に書き込む。「最初の一言」も「呼び水」も messages に入る。

それを A が拾うと、AIが自分の書いた文章から知見カードを作るループができる。タグは自己増殖し、知識地図はAIの言葉で埋まっていく。

✅ 守りは1行。is_agent = false の発言だけを拾う。

✍️
これは記事に書く価値がある。「エージェントが2体いる系では 片方の出力がもう片方の入力になる事故が起きる」──気づいて塞いだと書けると③の説得力が上がる

⚖️ 音声とチャットで危険の形が逆になる

🎤 音声
  • ❌ 誤変換する（知見 → 治験）
  • ❌ 話者を取り違える
  • ✅ 攻撃しにくい（声に出すのは目立つ）
  • ❌ 長い ＝ 高い（134分）
💬 チャット
  • ✅ 誤変換しない（本人が書いた文字）
  • ✅ 話者が確実（user_id が付く）
  • ❌ 攻撃しやすい（黙って貼れる）
  • ✅ 短い ＝ 安い
だからどうする軸
チャット由来のカードは信頼できるconfidence を高めに置く。裏取りが走る回数が減る＝安くなる②③
チャットのほうが攻撃されやすい入口の検査は同じだが、デモで攻撃を見せるならチャットが最適①
安い入力と高い入力が同じ流れに来るここでルーティングが効く。134分の音声と3行のチャットで同じモデルを使う理由がない②
📸
①の証拠が撮りやすくなった。これまでは「もくもく会で攻撃文を喋る」動画を撮る予定だった。チャットに1行貼るだけで済む。しかも画面に文字が残るので伝わりやすい

🎁 ついでに得すること

これまでの弱点チャットが入ると
コールドスタート（B10）
もくもく会を開くまで何も始まらない		チャットを打てばタグが育ち始める。会を開かなくても動く。デモも楽になる
企てのループが閉じきらない
部屋を立てたあと「で いつ話すの」が曖昧だった		部屋を立てた瞬間から会話できる。9日間のシナリオが素直につながる
呼び水が投げにくい
音声だけだとAIが割り込めない		B がチャットに1行書くだけ。実装がいちばん軽い形になる

💾 流すSQL

-- ① meetings を一般化する
alter table meetings rename to sessions;
alter table sessions rename column transcript_id to source_ref;
alter table sessions alter column source_ref drop not null;   -- チャットには無い
alter table sessions add column kind text not null default 'voice'
  check (kind in ('voice','chat'));

-- ② 参照名を合わせる
alter table knowledge_cards rename column meeting_id to session_id;

-- ③ messages をコアに。未処理かどうかを自分で持つ
create table messages (
  id         bigserial primary key,
  room_id    bigint not null references rooms(id),
  user_id    uuid references users(id),       -- AIの発言なら null
  body       text not null,
  is_agent   boolean not null default false,
  session_id bigint references sessions(id),  -- ★ null = まだ拾われていない
  created_at timestamptz not null default now()
);
create index on messages (room_id, session_id, created_at);

🔎 A が「閉じたかたまり」を探すクエリ

select room_id,
       min(created_at) as started_at,
       max(created_at) as ended_at,
       count(*)        as n
from   messages
where  session_id is null              -- まだ拾っていない
  and  is_agent = false          -- ★ AIの発言は入力にしない
group  by room_id
having max(created_at) < now() - interval '30 minutes'   -- 沈黙した
   and count(*) >= 5;                                    -- 短すぎるものは知見にならない
🔁
拾ったら sessions を1行つくって、そのメッセージ群の session_id を埋める。埋めた時点で二度と拾われない
