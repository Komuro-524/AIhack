🔁 同じタグで もう一度ライブを立てられるか

いまの設計だと 立てられない。しかも守り方が筋悪だった

quests.seed_key（タグ＋興味者の集合）に UNIQUE を付けていたので、1か月後に同じ顔ぶれでやりたくても衝突して立てられない。

しかも逆も成り立っていない。興味者が1人でも違えば seed_key は変わるので、翌日でもすり抜けて立ってしまう。厳しすぎて再開催を止め ゆるすぎて重複を許すという、いちばん悪い形になっていた。

🎯 「同じ」の定義が間違っていた。防ぎたかったのは「同じ組み合わせ」ではなく 「近すぎる時期の再開催」。
だから冪等キーではなく 進行中かどうか ＋ 前回からの間隔で持つのが正しい。

🔧 守り方を2つに分ける

防ぎたいこと守り方どこで
毎日同じ部屋が立つタグごとに進行中の企ては1つまで部分ユニーク制約。DBが保証する
終わった直後にまた立つ最短14日は絶対に立てないコードのハードリミット
14日を過ぎたあと 立てるべきかAI が判断するここが④の見せ場
🛡️
下限だけは人が決めて 上は AI に任せる。「自律性が上がるほど堅牢性の要求が跳ね上がる」への答えがこの形。暴走しても14日より短くはならないことをコードが保証する

🧠 「開催する意義があるか」の判断材料

ここを厚くするほど④が伸びる。数だけで決めないのが最初からの方針だったので、材料を並べる。

#材料どう効くか
1⏳ 前回からの間隔3日前なら却下。1か月なら検討に値する
2👥 顔ぶれの入れ替わり全員が前回と同じなら価値が薄い。半分が新しい人なら高い
3📈 興味の勢いこの1週間でタグが何人に新しく付いたか
4🗣️ 前回の反応何人来たか・コメントが何件あったか・あとで知見カードが何枚増えたか
5💬 アンコール前回のライブで「またこの会やりたいですね」と言われたか
6🧩 話題の進展前回と違う知見カードが溜まっているか（入門 → 実践 など）
7😮‍💨 相談役の負担また同じ人に頼むことになっていないか
🎁 ⑤のアンコール検出は ほぼタダで手に入る。
A はすでにトランスクリプトを読んでカードを作っている。そのついでに「またやりたい という趣旨の発言があったか」を構造化出力の1項目として出させるだけ。LLMの追加呼び出しはゼロ。

そして参加者が言った言葉が 次の開催の判断材料になるという形は、4層の輪がもう一周閉じるということでもある。

🚦 判断は3値にする

これが地味に効く。「やる／やらない」の2値だと AI は必ずどちらかに倒す。「まだ」を選べるようにすると判断が自然になり、見送りの理由も残る。

{
  "decision": "open" | "wait" | "skip",
  "confidence": 0.78,
  "reason": "前回から38日。興味者6人のうち4人は前回いなかった人。
             前回のライブで『次は実際に作るところを見たい』という発言があった",
  "next_review_at": "2026-11-05"      // wait のときだけ
}
📊
wait が quests.reevaluate_at に入る。「18回観測して 開いたのは3回 まだが9回 見送りが6回」と書けるようになって、判断ログの厚みが増す

📆 定期開催の設定画面は作らない

✅ 「毎月やる」を設定で持たせない。毎月興味が溜まるなら結果として毎月開かれる。設定画面がないのに定期開催になるのが、このプロダクトらしさ。

ピッチの一文 → 「定期開催の設定はどこにもありません。興味が溜まれば また開かれます」

✅ 決定：誘われた人だけ読める。画面モックの通り。

🚪 ただし穴が2つある

穴1｜あとから招待すれば 過去ログが読めてしまう

「誘われた人が読める」なら、終わったライブに今から誰かを招待すれば その人は過去の会話を全部読める。招待できる人が増えるほど、過去ログは静かに広がっていく。

✅ 守りは2本。

  • 招待できるのは 🎪B と そのライブのスピーカー だけ
  • 終了したライブには 誰も参加・招待できない ← これをDBに保証させる

開催中なら途中参加OK。入った瞬間にそれまでのコメントが見えるのは自然。終わった瞬間に扉が閉まるのが肝

穴2｜知見カードから トーク履歴に飛べてしまう

プロフィール画面に「トーク履歴 4件」という導線がある。知見カードは全社公開 なのに その先の元発言は参加者だけ ── この非対称を画面だけで守ると必ず漏れる。

✅ 二層にする。件数は見えてよい。中身は messages の RLS が弾く。クリックして初めて「このライブには参加していません」になるのが正しい挙動。

✍️
そしてもう1つ 地味だが本質的なルール。知見カードは全社公開なので、本文に発言をそのまま引用しない。必ず要約する。逐語で載せると「元発言は参加者だけ」が形だけになる。──A のプロンプトに1行入れるだけで済む

💾 SQL

-- 招待と参加を1枚で持つ。行があれば読める
create table live_participants (
  live_id    bigint not null references lives(id),
  user_id    uuid   not null references users(id),
  role       text check (role in ('speaker','listener')),  -- 参加したら決まる
  invited_at timestamptz,
  joined_at  timestamptz,
  primary key (live_id, user_id)
);

-- ① 誘われた人だけが元発言を読める
create policy "誘われた人だけ読める" on messages
  for select to authenticated
  using (exists (
    select 1 from live_participants lp
    where lp.live_id = messages.live_id
      and lp.user_id = auth.uid()
  ));

-- ② ★ 終了したライブには入れない（過去ログが後から広がらない）
create policy "開催中のライブにだけ参加できる" on live_participants
  for insert to authenticated
  with check (
    user_id = auth.uid()
    and exists (select 1 from lives l
               where l.id = live_id and l.status = 'live')
  );
🔒
②がいちばん効いている。「終了後は入れない」を画面のボタンを消すことで守ろうとすると必ず抜ける。DBが断るようにしておけば、どこから叩かれても同じ結果になる

そのうえで知見カードは同じ鍵でちゃんと見えるところまで並べて見せると、「公開するものと 守るものを分けている」が1画面で伝わる。
