# まなびの輪 記事ネタ帳

小室へ。記事を書くときに **岩田側のセッションでしか見えていない話** をここに集めています。
設計の理由・つまずいた場所・知らなかったこと・使える数字が中心です。
記事の構成（`manabi-no-wa-kiji-board.html`）の **どの層に使えるか** をタグで付けてあります。

## 📌 このファイルのルール（追記する人・AIへ）

- **追記のみ。** 既存のブロックは書き換えない・消さない
- 1セッション＝1ブロック。ファイルの **末尾** に `## 📓 セッション記録:` で始まるブロックを足す
- 中の見出しは下の **テンプレートと同じ7つ** にそろえる（無い節は「なし」と書く）
- 名前は **敬称略**（岩田 / 小室）。デモ用の架空社員の名前はそのまま書いてよい
- 読点は少なめ。見出しには読点を付けない

### 🚫 書いてはいけないもの

- APIキー・接続文字列・トークン・SupabaseのプロジェクトURL
- 実在の顧客名・社名・同僚の名前（岩田と小室以外の実名）
- 会議の文字起こしからの **逐語引用**（要約ならよい）

## 📓 セッション記録: 設計の言語化からDB構築・タグ付けエージェント稼働・夜間実装・朝の修正まで（9/20〜9/21朝）

### 🎯 このセッションでやったこと

- やりたいことの言語化 → 審査5軸への当てはめ → 穴の洗い出し（16個 → 危険43件まで網羅）
- エージェントを **3体に分割**。権限の分け方を決めた
- `DESIGN.md` と `README.md` を書き切った。**絶対に壊してはいけないルール** を14個（のちに15個）明文化
- Supabase を一から構築（13テーブル・全テーブルRLS・タグ辞書・権限）
- OrcaRouter をゼロから触って **エージェント別に上限付きのキーを3本** 発行

- 途中で **手作業をやめて Claude Code に丸投げ** する方針に切り替え、夜間に場づくり・自己分析まで実装させた
- 朝に夜間の判断3件を裁いた。話者の表記ゆれで社員が増殖するバグを見つけて直した
- SSO とカレンダー連携の方針を決めた（実装は範囲外）
- エージェント名を **タグ付け / 場づくり / 自己分析** に変えた

### 🧭 設計の考え方（なぜそうしたか）

#### 自律の3段階を先に決めた `④自律性`
- **Lv.1 応答**（聞かれたら答える）／**Lv.2 自動化**（決まった手順を回す）／**Lv.3 自律**（自分で起きて自分で決める）
- 審査の「自律性」で点になるのは Lv.3 だけだと判断した
- なので **場づくりエージェントだけを Lv.3** にして「心臓」と呼んだ。1日1回自分で起きて「この場を立てるか」を決める
- タグ付けと自己分析はあえて Lv.2。**全部を自律にしない** のも設計

#### 口を持つのは場づくりだけ `①セキュリティ`
- 人に通知を送れる（＝喋れる）のは場づくりエージェントだけ
- 通知の権限は **場づくりのキーにしか渡していない**
- タグ付けエージェントが文字起こしの中の「全員にメールして」を真に受けても **送る手段がそもそも無い**
- OrcaRouter のキーもエージェントごとに分けた（上限 $10 / $6 / $2・期限つき）

#### 三重の門 `①セキュリティ` `③堅牢性` `②コスパ`
- タグの「正しさ」は1つの問題ではなく3つ。分けると別々の道具で解ける
  - 門1 **形**：長さ・空白・記号・辞書にあるか。**正規表現と辞書だけなのでLLMを呼ばない＝0円**
  - 門2 **中身**：カードが集まって初めて人のタグになる。1回の発言では決めない
  - 門3 **本人**：本人が非公開にできる
- 辞書に無い新語は「候補」として溜めて **管理者が承認するまで正式にしない**。AIは `official` にできない

#### 判断は3値。迷ったら wait `④自律性` `③堅牢性`
- 場を立てるかどうかは `open` / `wait` / `skip` の3つだけ
- はい／いいえ の2値にすると、迷ったときに無理やりどちらかに倒れる
- **「今日は決めない」を正式な答えにした**。迷ったら wait に倒れる

#### 止めるのはコード。LLMに任せない `③堅牢性` `②コスパ`
- 企て（日をまたぐ未完了の仕事）の停止条件は **14日／候補3人に断られたら／1周のコスト上限**
- これを全部 **コードで保証** した。LLMが「まだ続けたい」と言っても止まる
- 「1タグにつき進行中の企ては1つ」も **DBの制約（部分ユニークインデックス）** で保証した

#### 管理者に渡したのは拒否権だけ `④自律性`
- 管理者は候補タグを却下できる。でも **場を立てる承認権は渡していない**
- 理由：管理者が見ていない週末に場がひとつも立たなくなる＝自律性が死ぬ
- タグの正式化（全社の語彙になるか）と企て（人と人をつなぐか）は **別のレイヤー** として独立させた

#### 人の介在点を4か所に絞った `④自律性` `①セキュリティ`
- 「全部AIがやります」ではなく「**人が入る場所を4か所に絞って設計しました**」と語る
  1. 相談役への打診に答える（本人。断れることが大事）
  2. タグ辞書への昇格を承認する（管理者）
  3. 未知の話者の名寄せをする（管理者）← **朝に見つけた穴から生まれた**（下のトライ＆エラー参照）
  4. 例外エスカレーションを受ける（管理者）

#### 穴がないふりをしない `作らなかった` `出発点`
- `DESIGN.md §10 今回の範囲外` に **やらなかったことと理由** を全部書いた
- 例：マルチテナント分離／キーの完全分離（防いでいるのは事故であって攻撃ではない）／カレンダー実連携／SSO

#### カレンダーは「取れるけど取らない」 `①セキュリティ` `作らなかった`
- 日程調整に必要なのは「空いているか」だけ。予定のタイトルは要らない
- Microsoft Graph に **空き／埋まりだけを返すAPI（`getSchedule`）** が公式にあった
- 返ってくるのは `022000110000` のような数字の列だけ（0=空き 1=仮 2=予定あり 3=外出中）
- 「A社との商談」という文字列がアプリに流れ込む経路が **最初から存在しない**
- 必要な権限も最小の `Calendars.ReadBasic`。全社のカレンダーを読める強い権限は **意図的に使わない**

#### 認証は自作しない `①セキュリティ` `作らなかった`
- ログインは Supabase Auth に寄せた。パスワードもセッションも自分では持たない
- だから SSO（Microsoft Entra ID / Google）は **設定を有効にするだけ** で入る構造になっている
- 今回は情シスの承認が要るので範囲外。ただし「メールアドレスは打たせず会社のアカウントから受け取る」設計にしてある
  - 理由：打ち間違い（`yamada@` → `yamda@`）でカレンダー連携が **静かに壊れる** から
  - 退職時に会社側でアカウントを止めればこのアプリにも入れなくなる
- メールアドレスは全社員に見える `users` テーブルに **複製しない**。タグを見せたいだけで名簿を配るつもりはない

#### 画面は「チャット」ではなく「ライブ」 `⑤独創性` `想い`
- 最初、岩田は LINE や Teams のような **グループチャット** を想像していた
- 小室のモックを見て「**インスタライブ型**」だったと気づいた（スピーカーは音声、リスナーはコメント）
- ライブには **必ず始まりと終わりがある** → 終わった瞬間にタグ付けエージェントが起きる、という引き金が自然に決まった
- 軽いモックを早めに出してもらったおかげで **手戻りがほぼ無かった**

### 🔥 トライ＆エラー（失敗 → 気づき → 直し方）

#### 1. 「自分の行だけ直せる」ポリシーで管理者に昇格できた `①セキュリティ` `出発点`
- **失敗**：`users` に「自分の行だけ update できる」ポリシーを書いた
- **気づき**：update のポリシーは **行は縛れても列は縛れない**。自分の行の `role` 列を `admin` に書き換えられてしまう
- **直し方**：`users` には update ポリシーを **作らない**。同じ罠が「自分のタグの強さを盛る」「他人の企てに割り込む」にもあったので、そこは本人しか呼べない関数（`security definer`）に置き換えた
- **記事で言えること**：「RLSを有効にした＝安全、ではなかった」

#### 2. 1回開いたタグで二度と場が立たなくなる `④自律性` `③堅牢性`
- **失敗**：同じ場が2回立たないように、企てに一意の鍵（`UNIQUE`）を付けた
- **気づき**：これだと **一度終わったテーマで二度と場が立たない**。逆に興味を持つ人が1人違うだけで重複が通る
- **直し方**：「**進行中の**企ては1タグ1つ」だけをDBで縛る（部分ユニークインデックス）。終わったら次が立てられる。再開催するかは3値判断に任せる

#### 3. 会議の文字起こしが公開リポジトリに出るところだった `①セキュリティ`
- **失敗**：作業メモ用のフォルダに実際の打ち合わせの文字起こしを置いていた
- **気づき**：提出するリポジトリは public になる。`.gitignore` に入っていなかった
- **直し方**：提出用リポジトリと作業メモ用リポジトリを **完全に分けた**。文字起こしは作業メモ側だけ

#### 4. APIキーをスクショに写した `①セキュリティ` `出発点`
- **失敗**：OrcaRouter のテストでエラーが出て、画面ごとスクショを撮って貼った。**キーの値が写っていた**
- **直し方**：すぐにそのキーを削除して作り直した
- **学び**：キーの画面は **値が見えている状態では撮らない**。一覧の伏せ字だけ。スクショは貼る前に必ず目視

#### 5. 権限エラーを見ていなかったので全部「辞書に無い」で落ちていた `③堅牢性` `出発点`
- **失敗**：タグ付けを流すと23件全部が「辞書に無い」で落ちた。`Power Automate` みたいに辞書にあるはずの語まで
- **気づき**：原因はタグではなく権限。Supabase の作成時に「新しいテーブルを自動で公開する」を **OFF** にしていたため、サーバー側の鍵にもテーブルを読む権限が付いていなかった。**辞書が空として読まれていた**
- **しかもエラーを確認していなかった** ので、候補タグの登録やユーザー作成も静かに失敗していた
- **直し方**：権限を明示的に付けるSQLを足し、**全部のDB操作にエラーチェック** を入れた。「辞書: 正式11件」と起動時に表示して、読めていることを目で見えるようにした
- **記事で言えること**：「失敗が静かなのがいちばん怖い」

#### 6. 「取り込み済み」と「権限エラー」を同じ扱いにしていた `③堅牢性`
- **失敗**：同じ文字起こしを2回入れたら弾く仕組みを作ったが、権限エラーでも「取り込み済みです」と表示されていた
- **直し方**：エラーコード（`23505` ＝重複）で区別した。**本物の重複だけ** を「狙いどおりの挙動です」と表示する

#### 7. 手でSQLを貼っていた `出発点`
- **失敗**：Claude に書いてもらったSQLを Supabase の画面に手で貼って実行 → 結果をスクショして貼り返す、を繰り返していた
- **気づき**：途中で「これ Claude Code に全部お願いすればよかったのでは」と気づいた
- **直し方**：そこから Claude Code に実装と実行を任せた。ただし **任せる前に「やっていいこと・ダメなこと」を決めた**（次の項目）

#### 8. 寝ている間にAIに実装させるための準備 `①セキュリティ` `③堅牢性` `④自律性`
- **心配**：Claude Code はデフォルトだとコマンドのたびに「実行していい？」と聞いてくる。寝ている間に投げると最初の1回で止まる
- **やったこと**
  - 許可リストを作った：ファイル読み書き・node・npm・git commit は許可
  - 禁止リストを作った：**`git push`**（寝ている間に公開リポジトリへ出ない）／**`rm`**（消す事故）／**`.env` の読み書き**（キーを見せない）
  - `CLAUDE.md` に絶対ルールを書いた（破壊的SQLは実行前に人間に確認、など）
  - 迷ったら **勝手に設計を変えず `QUESTIONS.md` に書いて先に進む** ルール
  - 1つのタスクで30分以上詰まったら次へ進む
- **結果**：朝起きたら場づくり・自己分析・デモデータ・証拠の自動化まで **8コミット** 進んでいた。迷ったことが3件 `QUESTIONS.md` に書いてあった

#### 9. 話者名の空白1個で架空社員が4人増えた ← いちばん大事 `①セキュリティ` `③堅牢性` `④自律性`
- **失敗**：デモ用の台本で話者名を「星野陸」と書いた。DBに登録されていたのは「星野 陸」（空白あり）
- タグ付けエージェントは名前の **完全一致** で人を探していたので「知らない人」と判断し、**架空社員を4人新しく作った**
- **安全装置が効いた**：Claude Code はこのゴミを消そうとしたが、`CLAUDE.md` の「破壊的SQLは人間に確認」と Claude Code 自身の安全装置に **止められた**。削除は実行せず `QUESTIONS.md` に「こういうゴミが残っている・消すSQLはこれ」と書いて朝を待った
- **気づき（設計の穴）**
  - 表記ゆれで同一人物が増殖する。実運用でも「岩田菜月」「岩田 菜月」で同じことが起きる
  - そもそも **タグ付けエージェントが社員を作れる権限を持っていた**。「口を持つのは場づくりだけ」の思想と矛盾していた
- **直し方**
  - 名前は **空白を落として比較** する（`星野陸` = `星野 陸`）
  - 名簿に無い名前が出ても **社員を作らない**。そのライブは「完了」ではなく「**要確認**（`needs_review`）」で止めて人に返す
  - これが **人の介在点の4つ目** になった。絶対ルールにも15番目として追加
- **記事で言えること**
  - 「AIに削除させない設計にしていたら、実際にAIが消そうとして止まった」
  - 「知らない人が出てきたら、勝手に作らずに人に返す」＝ **止まるべきところで止まる自律**

#### 10. AIで偽のスクショを量産しようとした `③堅牢性` `出発点`
- **考えたこと**：自己分析エージェントのテスト用に、AIで業務画面っぽいスクショをたくさん作ろうとした
- **気づき**：自己分析は **本物の画面を読む** のが仕事。AIが作った画面は文字が崩れていて配置も嘘なので、通っても「本物で動く」証明にならない。むしろ偽の合格が出て危ない
- **直し方**：社内情報が写る会社の画面も怖い → **このプロダクトを作っている自分の作業画面**（VS Code や Supabase）を使うことにした。社内情報ゼロで本物のUI
- **記事で言えること**：「このプロダクトを作っている自分を このプロダクトに分析させた」

#### 11. 小室のモックと衝突しかけた `出発点`
- **失敗**：`git status` を見たら小室のモック6ファイルに **1058行の差分** が出ていた
- **気づき**：中身は1行も変わっていなかった。**改行コード**（Windows と Mac の違い）が変わっていただけ
- **直し方**：押す前に元に戻し、以後は改行コードを勝手に変換しない設定にした。そのまま押していたら全行が競合していた

### 🔰 知らなかったこと → 分かったこと `出発点`

岩田はコードでエージェントを作るのは **初めて**（それまでは Copilot Studio などのローコードだけ）。このセッションで Claude に聞いたこと：

| 聞いたこと | 分かったこと（ひとことで） |
|---|---|
| `.gitignore` って何？ | 「このファイルは公開しないで」リスト。書いてもすでに追跡されているファイルには効かない |
| RLS って何？ | DBの **行ごとの鍵**。「誰がどの行を見られるか」をDB自身が守る |
| PR って何？ | 「この変更を取り込んでいいですか」というお願い |
| README / DESIGN / CLAUDE / AGENTS.md の違いは？ | 読む人が違う。README は審査員、DESIGN は設計の正、CLAUDE は Claude Code への指示 |
| コードでエージェントを作るって何？ | 「LLMに聞く → 道具を使う → 結果を見てまた聞く」の **ループ** を自分で書くこと。25行くらいで書ける |
| `.env.local` ってどこにある？ | 自分で作る。キーを置く場所で、絶対に公開しない |
| `NEXT_PUBLIC_` って？ | これが付いた変数は **ブラウザに焼き込まれる＝公開される**。サーバーの鍵には絶対付けない |
| Supabase のプロジェクトは個人開発のと分けるべき？ | 分ける。混ぜると権限もデータも混ざる |
| public リポジトリを提出したら主催者がデプロイしてくれる？ | してくれない。見られるのはコードと記事 |
| SQL Editor で Save しなくて大丈夫？ | 実行した結果はDBに残る。Save は「SQL文を保存するか」だけ |
| SQL Editor で RLS の確認ができる？ | できない。SQL Editor は **管理者の鍵で動くので RLS を素通りする**。一般社員になりきって確認する |
| OrcaRouter ってどう使うの？ | OpenAI と同じ書き方で、行き先を OrcaRouter に変えるだけ。モデル名を書かずに `orcarouter/auto` にすると勝手に選んでくれる |
| 寝ている間にAIに作業させるにはクレジットいくら要る？ | それより先に **権限の確認で止まる**。許可リストを先に作るのが本題だった |
| SSO だとログインにメールアドレスが要る？ | アカウントに **紐づくのは必須**。でも **打つ必要はない**。会社のアカウントから受け取れる |

**記事構成ボードの方針「初めてだった は出発点として書く」にそのまま使える。**

#### 部屋はリアルタイムではなく溜まってから立てる `④自律性` `②コスパ` `作らなかった`
- **検討した案**：いま画面で何の作業をしているかをAIがリアルタイムにタグ付けし 似た作業の人が同時にいたら部屋を立てる（作業通話アプリ型）

  - 業務時間内に使うと決めたので **作業中にずっと話せる部屋ができると仕事の邪魔** になる
  - 画面を読み続けるのでコストが高い
  - 作業が似ていても部署がまったく違う人同士だと集中できない
- **採った案**：興味ラベルが一定数溜まったら その知見を持つ人を探して部屋を立てる。リアルタイム性を捨てて **溜まったものから判断する**

  - 伏せても知識がある側には **自分が呼ばれた理由が分かってしまう**
- **採った案**：「相談役になってくれませんか」と **はい／いいえ で打診** する
  - ラベルの公開・非公開を本人が選べる設計と筋がそろう

- **外した理由**

  - 担当者を挟むと **人がOKしない限り動かない** 仕組みになり自律性が弱まる

- **直し方**：目印ファイルを消して `git reset` でインデックスを最新に揃えた
- **気づき**：「pushできた」と「手元が正常」は別。前回の「寝ている間は `rm` 禁止」と同じで **削除を禁止すると安全だが git が自分の後片付けをできなくなる**
- **記事で言えること**：「AIに消させない設定は 消すべきものまで残す」

#### 3. 隠しファイルにしても隠れない `①セキュリティ` `出発点`

- **直し方（提案）**：「隠す」ではなく「**最初から入れない**」
  - ラフやモックは公開して困らないので普通にコミットしてよい
  - 迷うものは `_scratch/` に置いて `.gitignore` に入れる。**絶対に push されない逃げ場** を作る
  - これなら提出のときに何も作業しなくて済む

### 🧭 設計の考え方（なぜそうしたか）

#### 話者は名前ではなく社員IDで持つ `①セキュリティ` `③堅牢性`
- 前のセッションでは名前の空白を落として照合する直し方をした。でも **同姓同名や通称** には効かない
- **選ばなかった案**：名前の照合をもっと賢くする（読み仮名・似ている度合い）→ どこまで賢くしても「間違えて別人に付ける」可能性が残る
- **採った案**：文字起こしの時点で **発言をアカウントに紐づける**。LLMには名前を見せず `[s12]` のような行番号だけ渡し 誰が話したかはコードが行番号から引く
- さらに DB に「そのライブの参加者でない人の発言は入れられない」という **複合外部キー** を張った。アプリのチェックを迂回して SQL を直接叩いても拒否される
- アカウントの無い人の参加は **認めない** と決めた（ログイン画面の設計に寄せた）

#### タグはAIが「候補」まで。正式にするのは人 `①セキュリティ` `④自律性`
- 流れ：**候補**（AIが見つけた新しい言葉）→ **格上げ候補**（直近30日に3つのライブ または 2人以上が語った）→ **正式**（管理者が承認）
- **選ばなかった案**：辞書にある言葉からしか選ばせない → 新しい分野が永遠に辞書に入らない
- **選ばなかった案**：語られた回数で自動で正式にする → 誰でも連呼すれば全社の語彙に入れられてしまう
- 格上げの条件は会社の規模で変わるので **設定値にした**（本番は管理者が画面で変える想定）
- 同じライブで同じ人が何度言っても **1回** と数える（1人の熱弁で格上げされないため）
- 育ちかけのタグもLLMに見せる。見せないと同じ話題が別の言葉に割れて **いつまでも数が集まらない**

#### 育ちかけのカードは話した本人と管理者にだけ見せる `①セキュリティ`
- **選んだ案（案B）**：候補の段階からカードも人のタグも作る。見え方は RLS で絞り **正式になった瞬間に一斉に見える**
- **選ばなかった案（案A）**：正式になるまでカードを作らない → 承認されたときに過去の発言を遡って作り直す必要があり 本人のプロフィールで「育ちかけ」を見せられない
- チャットは **そのライブの参加者だけ・開催中だけ** 投稿できるように絞った（元のポリシーは「自分として」しか見ていなかった）

#### Named Router は「構造化出力に対応しているか」で候補を絞った `②コスパ` `③堅牢性`
- 3体とも JSON で答えを受け取るので 非対応のモデルに振られた瞬間に壊れる
- 最安のモデルは非対応だった。**それまで動いていたのは偶然** だった
- タグ付けは量が多いので **最上位モデルに上がらない候補だけ** にして天井を付けた
- 場づくりにも最上位は置かない。候補の人はコードが作っていて LLMは選ぶだけだから

#### 受け皿は2段にした `③堅牢性`
- 1段目：OrcaRouter のルーター内の受け皿（ルーターが選んだモデルが落ちたとき）
- 2段目：アプリの受け皿（OrcaRouter そのものに届かないとき。別ベンダーのモデルを1回だけ直接呼ぶ）
- お店の店員が休んだら代わりを出すのはお店の仕事。**お店が閉まっていたら客が隣に行くしかない**
- 入力が原因の失敗（400）は別のモデルでも同じなので **やり直さない**

#### 途中で落ちたら やり直さずに人に返す `③堅牢性` `④自律性`
- 取り込み中の印が残ったまま次が始まったら **LLMを呼ばずに止まって「要確認」**
- 自動でやり直すと知見カードが **二重にできる**。どこまで書けたかを正確に知る手段が無いなら 人に返すのが正しい

#### 自己分析の画像はファイルにもしない `①セキュリティ`

- 誰の分析かは送られてきた中身ではなく **認証サーバーで確かめたログイン中の本人** で決める
- 撮影は画面を移っても続くようにした。ただし **再読み込みすると止まる**（メモリにしか無いから。これは仕様）

#### 画面では嘘を出さない `③堅牢性` `作らなかった`
- モックにある **閲覧回数・スキルの点数・Firewall の遮断件数** は出さなかった。元になるデータが無い
- 打診の画面に「興味のある人」は **人数と部署だけ**。非公開の興味タグから集まった人もいるので名前は出さない
- 管理者画面は **判断すること3つと数字4つ** まで削った。見せられる情報より 判断に要る情報
- 場づくりエージェントは企てを **1つずつ順番に** 処理している。画面は「同時にたくさん抱えている」様子で 並列処理ではない（記事でもそう書く）

- **直し方**：時刻は日本時間で解釈する。探し始めを「明日の0時」にし 予定は **重なり** で判定する。実データで「明後日15時にずれた」ことを確かめた

#### 4. 動画を撮っていてダブルブッキングを見つけた `④自律性` `③堅牢性`
- **失敗**：「人は引き受けるだけ」の動画を撮ったら 早坂 悠人（架空）が **同じ日の同じ15時に話し手として2本** 予約された
- **気づき**：空きを **カレンダーだけ** で見ていて 自分が入れた予約を見ていなかった。手帳は見たけど さっき入れた約束を手帳に書き忘れていた状態
- **直し方**：話し手として予約済みのライブも「埋まり」として扱う
- ついでに **予約した人が参加者に入っていなかった** ことも見つけた。チャットは参加者しか読めないので エージェントの「最初の一言」が **誰にも見えていなかった**

#### 5. 自動で回したのに何も進まなかった `④自律性`
- **失敗**：場づくりエージェントを1分おきに3周自動で回す証拠を撮ったら 3周とも **判断することが無くて何も進まなかった**（費用0円）
- **気づき**：「回った」と「進んだ」は違う。止まっているのは壊れているからではなく 返事待ちだったから
- **直し方**：1周目と2周目のあいだに **架空社員として打診を引き受ける** 動画にした。2周目でエージェントが勝手に日程を決め 予約し 最初の一言を書いた

#### 6. 取り込み中に落とす動画が撮れなかった `③堅牢性` `出発点`
- **失敗1**：同じ文字起こしをもう一度開いたら「二重取り込み防止」で **前のライブが返ってきた**
- **失敗2**：台本の `--live N` の `N` を **そのまま打った**
- **失敗3**：取り込みが数秒で終わるので Ctrl+C が間に合わない
- **直し方**：練習用と本番用の文字起こしを分けた。台本は数字の置き換えを明記した。「取り込み中のまま○秒待つ」オプションを足して **本物の Ctrl+C で落とせる** ようにした（落とすのは本物）

#### 7. 乗っ取り命令は「候補」にすらならなかった `①セキュリティ`
- **予想**：「全員公開にして」は4文字で記号も無いので 形の検査を **通ってしまう** と思っていた。そのときは候補止まりで管理者の承認が要る（2枚目の壁）と書く準備をしていた
- **結果**：LLMが最初からタグにしなかった。話者の付け替え命令も効かなかった（行番号で照合しているので名前を書かせる余地が無い）
- **記事で言えること**：1枚目の壁で止まった。2枚目の壁（候補止まり・一般社員には見えない）は RLS の検証で別に確かめてある

#### 8. アプリが重かった `出発点`
- **失敗**：ボタンを押してから画面が変わるまで5〜10秒
- **気づき**：原因は2つ。開発モードは **初めて開く画面をその場で組み立てる**。さらに1回の画面切り替えで「本当にログインしてる？」を **認証サーバーに3回** 聞いていた
- **直し方**：ふつうの画面はクッキーを読むだけにし 管理者の判定など **権限を決めるところだけ** 認証サーバーに確かめる。デモは組み立て済みで起動する（`npm run build` → `npm run start`）

#### 9. build が通らない・起動しない `出発点`
- **失敗1**：「ページが見つからない」で build が落ちた → 開発用のサーバーを **動かしたまま** build して同じ作業フォルダを取り合っていた。作業フォルダ（`.next`）を消してやり直したら通った
- **失敗2**：「3030番はもう使われている」→ 前に起動したサーバーが **裏で動いたまま** だった

#### 10. 選んだボタンが消えた `出発点`
- **失敗**：自己分析の時間を選ぶボタンを押すと そのボタンが消えた
- **気づき**：CSS の強さの順番で 選んだボタンが **白地に白文字** になっていた
- **直し方**：選んだ状態の色を強い指定で上書きした。プロフィールの公開ボタンも同じ不具合だった

#### 11. 小室の手元でアプリが開かなかった `①セキュリティ` `出発点`
- **失敗**：小室が起動したら「Supabase の URL とキーが無い」エラー
- **気づき**：鍵を置くファイルは **GitHub に上げていない** ので 小室の手元には無い
- **直し方**：鍵はDMで渡す。画面を見るだけなら **ブラウザ用の2つだけ** 渡し 全データを読み書きできる管理者の鍵は渡さない。デモで全部の鍵を持つのは1台だけにする

#### 12. Claude Code のクレジットが2回尽きた `②コスパ` `出発点`
- **失敗**：Claude Code が1つの作業で **12分考え込んだ** 直後に上限。買い足してもまた上限
- **直し方**：コードは Cowork が書き Claude Code は「適用・実行・コミット」だけにした。考える時は高いモデル・実行は安いモデルに自動で切り替わる設定にした。所要時間は **12分 → 6分**
- **もう1つ**：Cowork 側で作業を並列にしようとサブエージェントを2つ出したら **利用枠の上限** で止まった。サブエージェントは速くはなるが **安くはならない**

#### 13. Claude Code が確認なしで1行消した `①セキュリティ`
- **失敗**：費用の比較のために自分で一時的に足したデータを **確認なしで削除** していた
- **気づき**：自分で足した1行なので実害は無い。でもルールは「消す前に人に確認」
- **直し方**：次から依頼文に一言添える

#### 14. 小室の実名がデモに出るところだった `①セキュリティ`
- デモのデータに小室の実名が入っていたのを見つけて **全部架空の名前** にした。デモは完全に架空で通す

## 📓 セッション記録: 画面を使える重さにして 声をデモと設計に分けた（9/21 夜）

### 🎯 このセッションでやったこと

- 岩田と小室が触って出た画面の指摘を 何周も直した（自己分析の状態がページ移動で消える・カレンダーの月週日・知識地図のはみ出し・タグのドラッグ など）
- 画面が固まる問題を直した（先読みの嵐・読み込み表示がクリックを奪う・タブ切り替えのたびにサーバーへ行く・毎回の認証サーバー確認）
- 「企て」を **「ライブのタネ」** に言い換えた（育ち待ち → 話し手に相談中 → 日程を決め中 → ライブ予約済み → 開催済み）
- Chrome で通しの動作確認をした（ライブ作成→開始→コメント→終了→カード／打診→日程→予約／タグ承認／一般社員は管理者画面に入れない）
- ライブに **「マイクで話す」** を付けた。ブラウザの音声認識で文字にして参加者に共有する（声は届かない）
- 音声通話は **構成と壁の越え方まで設計** して書いた。サーバーを誰が持つか（標準プラン／専用環境プラン）も書き分けた
- 2つのリポジトリのドキュメントを今の実装に合わせた

### 🧭 設計の考え方（なぜそうしたか）

#### 声は「入口だけ差し替えられる」形にした `⑤独創性` `作らなかった`
- 文字起こしは最初から **社員ID付きの1行** で持っている。だから声の入口が「ファイル」「ブラウザのマイク」「将来の音声通話」のどれでも **タグ付けから先は1行も変わらない**
- **選ばなかった案**：会議ツールの文字起こしを取り込む → 話者が **表示名でしか** 返ってこない。名前で人を決めない方針に戻ってしまう
- **選ばなかった案**：今回の提出までに音声通話を作る → 「つながった」を人が2台以上で確かめないと動いたと言えない。穴がないふりはしない

#### マイクの発言は「誰の発言か」をサーバーが決める `①セキュリティ`
- ブラウザから社員IDは受け取らない。サーバーが **ログイン中の本人・配信中・このライブの話し手** を確かめてから 本人のIDで書く
- 文字起こしの表にはブラウザ向けの書き込み口をそもそも作っていない

#### 音声通話の壁は「降りていく道」で越える `①セキュリティ` `③堅牢性`
- 会社のネットワークは速い道（UDP）を止めがち。**UDP → TCP → 443番のTLS** と自動で降りる道を用意して どれかで必ず通る形にした
- 入場券はサーバーだけが出す。中身は社員ID・期限10分・その1部屋だけ・聞き手は聞くだけ
- 端末間暗号化は **サーバーで文字にできなくなる** ので採らず「決めた場所から声を出さない」で守る

#### サーバーを誰が持つか `⑤独創性`
- 標準プラン：開発元が国内クラウドで運用 → **契約した日から使える**
- 専用環境プラン：導入企業のテナントに構築 → 声も文字も社外に出ない代わりに数週間かかる
- どちらでも残る関門は **情シスの通信許可** と **セキュリティ審査**。443番だけで通る作りと審査の回答集で軽くする

### 🔥 トライ＆エラー（失敗 → 気づき → 直し方）

- だから「ページを送って全部読む」に加えて **天井を超えたら止めて知らせる** 形にした。黙って切らない
