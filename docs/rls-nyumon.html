Supabase · 5分

🔐 RLS ってなに

🎯 「この行は誰が見ていいか」をテーブル自身に書いておく仕組み。
書いておくと DBが勝手に WHERE を足してくれる。
Row Level Security ＝ 行レベルセキュリティ。Postgres の機能。

🧠 SQLで見るとこうなる

これがいちばん腑に落ちる説明。

-- アプリが投げるクエリ
select * from user_tags;

-- DBが実際に実行するもの（RLSが勝手に足す）
select * from user_tags
where (visibility = 'public' or user_id = ログイン中の人);
💡
つまり「絶対に外せない WHERE 句」をテーブルに貼り付けておく機能。アプリ側が書き忘れても、DBが必ず足す

🚪 なぜ Supabase では必須なのか

前に作った Java の EC サイトと、いちばん違うのがここ。

🏢 これまでのWebアプリ
🌍 ブラウザ利用者
↓
🛡️ サーバー自分で書いたJavaの処理
↓
🗃️ DB
🛡️ 門番はサーバー。「この人にこの行を返していいか」を自分で書いたコードが判断していた。ブラウザはDBに直接さわれない
☁️ Supabase
🌍 ブラウザ利用者
↓
🚫 サーバーがいない直接つながる
↓
🗃️ DB ＋ 🛡️RLS門番がDBの中にいる
🛡️ 門番がDBの中に引っ越した。ブラウザがDBを直接たたくので、RLSを書かないと門番が誰もいない
🏠
たとえるならマンションのオートロック。今までは1階に受付の人がいて、来た人を確認してから通していた。Supabase は受付がいなくて、誰でも各部屋の前まで来られる。だから部屋ごとに鍵が要る

⚠️ 書かないとどうなるか

anon key は ブラウザに焼き込まれている ＝ 公開されている

NEXT_PUBLIC_SUPABASE_ANON_KEY は、ページのソースを見れば誰でも拾える。それは設計どおりで、問題ない。anon key は「公開される前提の鍵」だから。

問題はその鍵で何ができるか。RLSを書いていないと、拾った人が自分のPCから

select * from user_tags;

を投げるだけで、非公開にしたはずのタグも全部返ってくる。画面で隠していても関係ない。画面を通さずにDBを直接たたかれるから。

🎯
だから user_tags.visibility = 'private'（隠しタグ）は、RLSを書いて初めて本物になる。ここは採点①で突かれたら一発で崩れる場所

🧨 よくあるハマりどころ

起きること理由
RLSを有効にしたらデータが1件も出なくなった有効にしてポリシーを1つも書かないと全部拒否になる。「誰も入れない部屋」の状態。ポリシーを書けば出る
エージェントは動くのに画面だけ空っぽ正常。service_role キーはRLSを素通りするので、サーバー側のエージェントは影響を受けない
Supabase の画面で赤い警告が出ているRLSが無効なテーブルがあると教えてくれる。提出前に全部緑にする

📋 学びの輪ではこうする

テーブル読める人書ける人
users社員なら全員自分の行だけ本人
tags社員なら全員🎙️A だけ
knowledge_cards社員なら全員🎙️A だけ
user_tags公開タグは全員 ／ 非公開は本人だけ公開設定だけ本人。中身は 🎙️A 🔍C
invitations自分宛だけ返事だけ本人
quests / quest_steps誰も読めない（エージェント専用）🎪B だけ
agent_runs誰も読めない全エージェント

※「🎙️A だけ」は service_role キーで動くサーバー側という意味。ポリシーを作らなければブラウザからは書けない

💾 そのまま貼れるSQL

テーブルを作ったあとに、これを実行する。

-- ① まず全テーブルで有効にする（これを忘れると素通り）
alter table users           enable row level security;
alter table tags            enable row level security;
alter table knowledge_cards enable row level security;
alter table user_tags       enable row level security;
alter table quests          enable row level security;
alter table quest_steps     enable row level security;
alter table invitations     enable row level security;
alter table agent_runs      enable row level security;

-- ② 社員名簿：ログインしていれば読める／自分の行だけ直せる
create policy "社員は全員読める" on users
  for select to authenticated using (true);

create policy "自分の行だけ直せる" on users
  for update to authenticated using (id = auth.uid());

-- ③ タグ辞書と知見カード：読むのは全員／書くのはエージェントだけ
--    （insert のポリシーを作らない＝ブラウザからは書けない）
create policy "タグは全員読める" on tags
  for select to authenticated using (true);

create policy "知見カードは全員読める" on knowledge_cards
  for select to authenticated using (true);

-- ④ ★ ここが本番：公開タグは全員／非公開は本人だけ
create policy "公開は全員 非公開は本人だけ" on user_tags
  for select to authenticated
  using (visibility = 'public' or user_id = auth.uid());

create policy "公開設定は本人が変えられる" on user_tags
  for update to authenticated using (user_id = auth.uid());

-- ⑤ 打診：自分宛だけ見えて 自分だけ返事できる
create policy "自分宛の打診だけ見える" on invitations
  for select to authenticated using (user_id = auth.uid());

create policy "自分宛の打診に返事できる" on invitations
  for update to authenticated using (user_id = auth.uid());

-- ⑥ 企て・判断ログ・実行記録はポリシーを作らない
--    ＝ ブラウザからは一切見えない。エージェント（service_role）だけが触る
🔑
auth.uid() は「いまログインしている人のID」。Supabase が自動で埋めてくれるので、こちらで渡す必要はない

📸 これは証拠にもなる

🎬
①の証拠が1本増える。ログイン中の人の anon key で、他人の非公開タグを select しても0件しか返ってこない画面。「画面で隠した」ではなく「DBが返さない」を見せられる
