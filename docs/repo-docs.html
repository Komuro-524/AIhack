📚 リポジトリの .md 一族

README・DESIGN・ARCHITECTURE・CLAUDE・AGENTS … 何がどう違うのか。

🎯 全部「誰が いつ読むか」で分かれているだけ。
中身が違うのではなく読む相手が違う。そう思うと一気に整理がつく。

そして 今回 ARCHITECTURE.md は作らなくていい。理由は下に。

🗂️ 5つの棚に分かれている

🚪 玄関
README.md
初めて来た人が最初に開く。「これは何？ なぜ作った？ どう動かす？」
読む人：訪問者・審査員・未来の自分。いちばん読まれる1枚
🧠 なぜこう作ったか
DESIGN.md
docs/adr/*.md
判断と根拠を置く。仕様・データモデル・ルール・やらないと決めたこと。
読む人：一緒に作る人と そのAI。「なぜ」に答える棚
ADR は「1つの決定＝1ファイル」で歴史を積む形式。長く続くプロジェクト向け
🗺️ どこに何があるか
ARCHITECTURE.md
コードの地図。どのフォルダが何を担当し どこから読み始めればいいか。
読む人：新しく入った開発者。コードが大きくなってから効く
🤖 AIへの作業指示
CLAUDE.md
AGENTS.md
.cursorrules など
このリポジトリで作業するときの約束。「先にこれを読め」「テストが通らないコミットはするな」
読む人：AI。CLAUDE.md は Claude Code 向け、AGENTS.md はツール横断の共通規格
🤝 参加と履歴
CONTRIBUTING.md
CHANGELOG.md
LICENSE / SECURITY.md
外の人が関わるようになってから要るもの。PRの出し方・変更履歴・権利・脆弱性の報告先。
読む人：他人。公開して人が集まってから作ればいい

🤔 いちばん紛らわしい2つ

ARCHITECTURE.md
🗺️ 物理の話
  • フォルダ構成
  • モジュールの依存関係
  • どのファイルが何をするか
  • どこから読み始めるか
📦
コードを案内するための地図
DESIGN.md
🧠 論理の話
  • 何を解くのか
  • どんなルールで動くのか
  • データはどう持つのか
  • なぜそう決めたのか
💡
判断を残すための記録
📏
見分け方：「コードを全部消しても意味が残るか」。
残るなら DESIGN.md、残らないなら ARCHITECTURE.md

⚠️ AGENTS.md の罠

「作るエージェントの設計書」ではない

AGENTS.md は AIコーディングツールへの作業指示書。「このリポジトリで作業するAIへのルール」を書く場所で、CLAUDE.md のツール横断版。

いま学びの輪は3体のエージェントを作っているので、ここが混ざりやすい。

  • 🤖 A・B・C の設計 → DESIGN.md §3（作るもの）
  • 🛠️ Claude Code への指示 → CLAUDE.md（作る道具への指示）

名前が似ているだけで別のレイヤー。

✅ 今回どうするか

ファイル今回理由

💭 CLAUDE.md だけ 少し迷う

外したまま入れる
リポジトリがきれいに見える。作業メモが混ざらない 小室さんのClaudeが毎回確実に DESIGN.md §8 を読むようになる。
審査でも「自分たちが使うAIにもガードレールを敷いた」と言える

入れるなら3行で足りる。作業メモにはならない。

# 作業を始める前に

**必ず `DESIGN.md` を読むこと。**

- 実装の前に `DESIGN.md §8 絶対に壊してはいけないルール` を読み直す
- 決めたことは会話に残さず `DESIGN.md` に書き戻す
- テーブルを作るときは RLS を同じ回で書く
🙋
どちらでもよい。無くても DESIGN.md を最初に渡せば同じなので、今夜は気にしなくていい
