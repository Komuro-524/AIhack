🗃️ テーブルに足すもの

少ない。ほとんど既にある仕組みに乗る。

-- ① 管理者かどうか
alter table users add column role text not null default 'member'
  check (role in ('member','admin'));

-- ② 人が禁止したものを AIが弾いたものと分ける
alter table tags
  drop constraint tags_status_check,
  add  constraint tags_status_check
       check (status in ('candidate','official','rejected','banned'));
--   rejected = AIが弾いた  /  banned = 人が禁止した

alter table tags add column reviewed_by uuid references users(id);
alter table tags add column reviewed_at timestamptz;
alter table tags add column review_note text;
🎁
禁止にしたタグの後始末は要らない。画面に出すときの条件はもともと t.status = 'official' なので、banned にした瞬間にそのタグが付いていた全員から自然に消える。消す処理を書かなくていい

🔐 RLS を1本足す

-- 候補と弾いた語は 管理者だけが見える
create policy "管理者は全部のタグが見える" on tags
  for select to authenticated
  using (
    status = 'official'
    or exists (select 1 from users
               where id = auth.uid() and role = 'admin')
  );

-- 禁止と復活も管理者だけ
create policy "管理者だけタグを裁ける" on tags
  for update to authenticated
  using (exists (select 1 from users
                 where id = auth.uid() and role = 'admin'));
⚠️ ここを RLS で書くのが大事。「管理者ビューのURLを知らなければ見えない」は守りではない。一般社員の鍵では候補タグが1件も返らないことをDBに保証させる

📸 数字がひとつ増える

🔢 AIが弾いた数 と 人が直した数を並べられるようになった。

「42タグのうち AIが7つ弾き 人が禁止にしたのは1つ 戻したのは1つ」

人が直した数が少ないほど AIの判定が当たっている証拠になる。①と④の両方で使える数字で、しかも tags を group by status するだけで出る。
