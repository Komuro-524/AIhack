実装 · エージェントとは何か

🤖 コードでエージェントを作るとは

Copilot Studio が裏でやっていたことを 自分で書くだけ。特別な部品は存在しない。

🎯 「エージェント」という名前のライブラリも ファイル形式も存在しない。
実体は LLMを呼ぶ → 返ってきた指示で関数を実行する → 結果をまた渡す のくり返し。ただのループ。

だから AGENT.md のような決まったファイルを置く必要はない。

🆚 Copilot Studio と何が違うか

やることCopilot Studioコードで書く場合
役割を教える画面に「指示」を書くシステムプロンプト（ただの文字列）
道具を持たせるアクションを画面でつなぐ関数を書いて スキーマをLLMに渡す
会話を回すMicrosoftが裏でやる自分で for ループを書く ← ここだけ新しい
モデルを選ぶ選べないOrcaRouter に任せる
置き場所MicrosoftのクラウドVercel の API Route
💡
知らなかったのは「ループを自分で書く」ところだけ。あとは Copilot Studio でやっていたことと同じ

🔁 エージェントの中身は6段

1
役割を渡す　システムプロンプト（「あなたは記録係です。ルールは…」）
2
道具の一覧を渡す　「こういう関数が使えます」という説明だけ。中身は渡さない
3
LLMに聞く　返ってくるのは答えか 「この道具をこの引数で使って」という依頼
4
道具を実行する　ここは自分のコード。DBを引く・通知を送る。引数を検証するのもここ
5
結果をLLMに返す　「その関数の答えはこれでした」
6
道具を使わなくなったら終わり　LLMがそのまま答えを返してきたらループを抜ける
🔄
3〜5 をくり返す。これが「エージェントループ」。Copilot Studio が裏で回していたのもこれ

💻 実際に書くとこれだけ

25行。これがエージェントの全部。

import 'server-only'          // ★ ブラウザから読まれたらビルドが落ちる
import OpenAI from 'openai'

const ai = new OpenAI({
  baseURL: process.env.ORCA_BASE_URL,
  apiKey:  process.env.ORCA_KEY_RECORDER,   // ★ Aのキー。通知権限は無い
})

export async function runAgent(system, userInput, tools) {
  const messages = [
    { role: 'system', content: system },
    { role: 'user',   content: userInput },
  ]

  for (let i = 0; i < 10; i++) {          // ★ 停止条件。止まれるようにする
    const res = await ai.chat.completions.create({
      model: 'manabi-recorder',              // ★ Named Router の名前。モデル名を書かない
      messages,
      tools: tools.map(t => t.schema),
    })

    const msg = res.choices[0].message
    messages.push(msg)

    if (!msg.tool_calls) return msg.content   // 道具を使わない ＝ 終わり

    for (const call of msg.tool_calls) {
      const tool = tools.find(t => t.name === call.function.name)
      const args = JSON.parse(call.function.arguments)
      const result = await tool.run(args)      // ★ この中で引数を検証する
      messages.push({ role: 'tool', tool_call_id: call.id,
                      content: JSON.stringify(result) })
    }
  }
  throw new Error('上限に達した')              // ★ 🚨例外の門へ
}
✅ 設計で決めたルールが そのままコードの3か所に落ちている。
  • i < 10 ＝ 停止条件はコードで持つ（DESIGN.md §8-10）
  • model: 'manabi-recorder' ＝ モデル名をコードに書かない（§9）
  • tool.run(args) の中 ＝ LLMの出した引数を照合する（§8-2）

🎁 プロンプトを .md に切り出すのを強く推す。これが「エージェントフォルダに指示文書を置くイメージ」にいちばん近い形。
  • コードを触らずに調整できる
  • diff が読める（何をどう直したかが残る）
  • 審査員が読める ← これが大きい
「どんなルールでAIを動かしたか」がリポジトリの見どころになる。④の証拠として効く。

🧩 サブエージェントに切ればコストが下がる？

下がらない。そこは分ける理由にならない

コストを決めるのは「何体いるか」ではなく「どの呼び出しにどのモデルを使うか」。同じ1体の中でも呼び出しは何回もある。

🎙️ A の中の呼び出し使うモデル
① 知見っぽい発言だけ拾う（足切り）無料 Union Alpha
② 残った発言をカードにする安い担当
③ 怪しいタグだけ検証する安い担当
④ 昇格を提案するか最終確認強い担当

これを「4体のサブエージェント」と呼ぶ必要はない。呼び出しごとにモデルを変えるだけで、それは OrcaRouter の Named Router の仕事。

📐 エージェントを分ける基準は コストではなく この3つ。
  • トリガーが違う（いつ起きるか）
  • 権限が違う（何ができるか）
  • 壊れ方が違う（どう守るか）
A・B・C はこの3つが全部違う。だから3体で正しい。そしてこれ以上増やす理由はいまのところ無い。

⚠️ ふたつの「サブエージェント」は別物

意味今回
Claude Code のサブエージェント開発中にClaudeが仕事を分担する仕組み。調べ物を別のClaudeに投げるなど作るものとは無関係
プロダクトのエージェントA・B・C。自分たちが書くコードこれを作る
🏷️
同じく AGENTS.md も 「作るエージェントの設計」ではなく「コーディングAIへの作業指示」。今回は DESIGN.md §3 が設計を持っているので作らなくていい
